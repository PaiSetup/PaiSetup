# PaiSetup

PaiSetup configures a machine (packages, GUI, shell, keyboard/locale, dotfiles, uninstalling
bloatware, etc.) in an automated, repeatable way. It targets Arch Linux, Debian-like Linux and
Windows. Most of it is Python; a handful of one-time bootstrap scripts are Bash/PowerShell.

## Two-phase setup: `pre_setup` then `setup.py`

Setting up a machine happens in two phases:

- **`pre_setup/`** contains OS-specific scripts (Bash for Linux, PowerShell for Windows) that lay
  the foundation the rest of the framework needs (e.g. partitioning/fstab concerns, bootloader,
  base package manager setup). These are meant to be run **exactly once**, before anything else.
  Running them again can leave the system in an inconsistent state.
- **`setup.py`** is the main entry point and is **idempotent** - it is safe, and expected, to run
  repeatedly as the configuration evolves. Each run re-applies the current configuration; steps
  that detect nothing has changed do little to no work.

`setup.py` needs elevated privileges to do its job, since many steps write to system locations or
install packages: administrator on Windows, and passwordless (or interactive) `sudo` privileges on
Linux. On Linux, `setup.py` itself is run as the regular user, not via `sudo` - steps prefix the
individual commands that need root with `sudo` themselves.

## Setup modes and steps

The unit of work is a `Step` (see `steps/step.py`): a self-contained piece of configuration such as
installing a package group, configuring the shell, or setting up a GUI compositor. A step can
implement any of: declaring dependencies on other steps (pushing data to them or pulling data from
them), and `perform()` - the actual work.

`perform()` is only called if the concrete step class overrides it directly (see
`Step.is_method_overriden()`); an implementation inherited from a base class doesn't count. A step
deriving from a base class that implements `perform()` (e.g. `NotesStepBase`, `DushStepBase`) has to
override it, even if only to call `super().perform()`.

A **setup mode** (`utils/setup_mode.py`) represents one kind of machine to configure and owns the
list of steps to run for it - e.g. an Arch desktop, a Debian "casual" install, a Windows machine.
Each mode is a small class exposing a name and a `get_steps(...)` method that builds and returns the
step list; modes can also report whether they're compatible with the current machine, which is used
both to validate the previously used mode and to auto-select a mode when there's exactly one
suitable candidate. Modes are discovered dynamically per package rather than hardcoded in one place,
which is what makes the plugin system (below) possible. `setup.py` resolves the desired mode (from
the `--mode` flag, or the last mode used, or auto-detected), asks it for its steps, and hands them to
the execution engine, which filters them (whitelist/blacklist), resolves dependencies between them,
and calls `perform()` on each enabled step in order.

## Services

Steps get access to a small set of shared services (`utils/services/`), injected once at startup
and available on every `Step` instance:

- **Env** - tracks environment variables the setup wants to define, mediates between "set for the
  current process" and "written out for future shell sessions", and exposes the resolved home
  directory and current user.
- **FileWriter** - the standard way steps create or modify files on disk. It understands "sections"
  and file-type-aware comment markers, so multiple steps can safely contribute lines to the same
  generated file, and it auto-adds a "do not edit, generated by PaiSetup" header. Files are
  recreated from scratch at the start of a run and rebuilt incrementally as steps register content,
  with a final flush at the end. It also has helpers for symlinks, patching `.ini`/`.desktop` files,
  and transparently escalating with `sudo` when a direct write hits a permission error.
- **Logger** - structured, indentation-aware console logging with timing between log lines, plus a
  warnings mechanism (optionally attaching a saved report file) that gets echoed at the end of the
  run.
- **PerfAnalyzer** - records timing of logged operations to help spot slow steps.
- **Paths** - a registry of well-known paths (`KnownPath` enum; some values exist only on
  Windows or only on Linux). Home, the PaiSetup root and its build and secret dirs are set automatically; the rest are set by the
  steps owning them (`FoldersStep` on Windows, `HomeDirectoryStep` on Linux) in their `__init__()`.
  Other steps may query them in any phase after initialization (push, pull, perform), but never in
  `__init__()`, since step construction order is undefined. Home (`self._paths.home()`) and the
  PaiSetup root, along with `BuildDir` and `SecretDir`, are the exception - they're set before any step exists, so they can be queried anywhere.
- **SetupFlags** - options of the current run, resolved from the command line before any step
  exists, so they can be queried anywhere (`self._flags`). Besides `install_packages`, these are the
  `strict_*` options: by default the run is as fast as possible and skips work it believes is already
  done (git fetches, downloads, builds, reinstalls); each `--strict_*` flag turns one kind of shortcut
  off, and `--strict_full` turns off all of them. Steps read these instead of taking such flags as
  constructor arguments.

Services are wired up once in `setup.py` and assigned onto the `Step` base class, so any step method
can just use `self._env`, `self._file_writer`, `self._logger`, etc. without receiving them as
constructor arguments.

## Dependency dispatcher

Steps intentionally don't reference each other directly - instead they declare dependencies through
the `DependencyDispatcher` (`utils/dependency_dispatcher.py`), which acts as a broker. A step can
mark one of its own methods as a dependency handler; other steps then "call" that dependency by name
through the dispatcher without knowing which step (or how many steps) actually implement it.

There are two kinds of dependencies:
- **Push** - a step sends data to whichever step(s) registered a handler for it (e.g. "here are
  packages that need to be installed"). Multiple handlers can receive the same push.
- **Pull** - a step asks for data back from exactly one other step that registered a handler for it
  (e.g. "give me the directory you resolved for X"). Only one handler is allowed per pull dependency.

All push dependencies are processed before any pull dependencies. If a step depends on something
nobody provides, that's an error (unless dependency resolution is explicitly relaxed) - this is what
lets steps declaring a dependency on a package-installing step get implicitly enabled even if they
were otherwise filtered out, and what turns a missing plugin/step into a clear failure instead of a
silent no-op.

## Package steps

Each OS has its own package-installing step (Arch/`yay`+pacman, Debian/`apt`, Windows/`choco`), and
the specifics of any one of them matter less than the role they play: almost every other step
depends on the package step by pushing package names to it rather than installing anything
themselves. This keeps installation centralized (dedupe, single upgrade pass, consistent logging).

The project grew up around Arch, so Linux steps express their dependencies in Arch package names no
matter which distro is being configured, and the Debian step translates them into what `apt`
understands: same name (the default), a hardcoded rename (sometimes one Arch package becoming
several apt ones), dropped entirely when it's Arch-specific, or delegated to a small install script
next to the step when there's no apt package but we still want the software.

Windows is outside this scheme - its steps are disjoint from the Linux ones and push Chocolatey
names in the first place, so there is nothing to translate. Instead, the Windows step keeps
per-package *installation* knowledge, since Chocolatey packages wrap wildly different installers:
installer flavor, the arguments needed to pick an install directory, desktop shortcuts to clean up,
and startup entries the package creates. Always verify `PackageInfo` knows how to handle a package
whenever you add a new one. If it doesn't, ask the user about the installer type and other
parameters.

## Notable utilities

- **`run_command`** (`utils/command.py`) - the standard way steps shell out. It wraps
  `subprocess.Popen` with composable `Stdin`/`Stdout` descriptors (ignore output, capture and return
  it, print live, or write to a file), optional background execution, and raises on a non-zero exit
  code so failures aren't silently swallowed. Almost every step that touches the outside world (git,
  package managers, compilers, system tools) goes through this instead of calling `subprocess`
  directly.
- **`run_powershell_command`** - a Windows-only convenience over `run_command` that wraps one or
  several command strings into a single `powershell -Command` invocation, joining multiple lines
  with `;`. Used whenever a step needs Windows-specific behavior with no direct shell equivalent
  (registry edits, shell verbs, `Invoke-WebRequest`, etc.), while still going through the same
  error-checked execution path as `run_command`.
- **External projects** (`utils/external_project.py`) - helpers for steps that pull content from
  outside the package manager: cloning/updating a git repo to a given revision, running CMake/Make
  with patches applied first, and downloading/unzipping a project straight from a GitHub zip or
  release asset. Building from source is one common use, but these are just as often used to fetch
  things that are never compiled - notes and dotfile repos, icon themes, fonts, prebuilt binaries -
  so steps don't reimplement "clone, checkout, update" or "download and unpack" each time.
- **FileWriter** (`utils/services/file_writer.py`, see also Services above) - worth calling out again
  as a utility in its own right: it's the shared abstraction for "many independent steps need to
  append configuration into the same handful of dotfiles/scripts" without stepping on each other or
  clobbering manual edits, since everything it touches is clearly marked as generated.

## Plugin system

Beyond the built-in setup modes for Arch/Debian/Windows, the framework supports plugins: extra step
packages that live under a dedicated plugins directory inside `steps/`, are excluded from version
control, and are picked up automatically at runtime without any built-in code needing to know their
names. A plugin is a normal Python package that defines one or more setup mode classes the same way
a built-in mode does (a name, compatibility check, and a step list), plus a small list of those
classes so the discovery logic knows what to instantiate. It's free to define its own steps and/or
reuse existing public steps.

This exists so machine- or environment-specific configuration that shouldn't be part of the public
project (e.g. anything tied to a particular workplace or personal setup only relevant to one
machine) can still be selected as an ordinary setup mode via the normal `--mode` flag, live
side-by-side with the built-in modes, and simply be absent - with zero effect on behavior - on any
machine that doesn't have that plugin directory checked out.

Since plugins aren't part of this repo's history, each one may keep its own `CLAUDE.md` describing
what it's for - check inside a plugin's directory for one before assuming this file is the full
picture. A plugin may also ship Claude Code skills under `steps/plugins/<name>/.claude/skills/`.
Those are nested below the repo root, so they only register once a file inside the plugin directory
has been read - reading the plugin's `CLAUDE.md` is enough, and worth doing early when a task
touches a plugin, so its skills are available for the rest of the session.
